Design Note

Labware Resolution and the Initial-State Oracle

How a labware nickname is matched to a config label, and how the uploaded initial-state map (the oracle) drives that match for contents-bearing labware.

1. The problem

Instructions name labware by nickname — "source plate", "tube rack". The robot needs the exact config label.

Turning a nickname into a config label is the labware-matching problem. The instruction speaks in the user's words; the deck is defined in config labels. Something has to bind the two.

2. How the current resolver works (no oracle)

For each nickname the resolver has the set of wells the instruction references for it, then runs three steps (_resolve_one, resolver.py:569):

  • Capability filter — keep only config labwares whose physical well layout contains every referenced well (wells ⊆ valid_wells). This is geometry truth. Unknown layouts are kept (fail-open).
  • Type filter — keep candidates whose category matches the wording: "tube" → tuberack/aluminumblock, "plate" → wellplate, "tip" → tiprack. No cue → keep all.
  • Dispatch on survivors:
    • 1 survivor → deterministic (confidence 0.95, no LLM).
    • 2+ survivors → the LLM picks among the physically valid candidates (0.85) — the guesswork step.
    • 0 survivors → a detected namespace split, or unresolvable → the user picks.

3. The new signal: the oracle's occupied-well shapes

The uploaded initial-state map gives, per config label, the exact set of wells filled at the start. That is independent evidence the resolver never had — the actual shape of what is loaded.

4. The shape-matching logic

Inputs

  • I(n) — for each nickname, the wells it holds initial contents in: explicit "X contains Y" mentions plus inferred source wells. Not destination-only wells — those are empty at t=0 and will not appear in the oracle.
  • E(c) — for each config label, the set of wells the oracle fills.

Rule

  • Candidates C(n) = { c : I(n) ⊆ E(c) }. Subset, not equality — the instruction usually names only some of the wells the oracle fills.
  • Substance as a soft filter — where a well is in both, the substances should agree (lenient: "lysis buffer" vs "lysis" still matches). A clear contradiction drops that candidate and is itself a conflict to surface. Wells are the hard signal; substance breaks ties and catches conflicts.
  • Global one-to-one assignment — per-nickname uniqueness is not enough; two nicknames pointing at the same label is a conflict. Assign every nickname whose candidate set is a singleton, remove that label from the others, and repeat (constraint propagation). Only the bindings that come out forced become hints.
  • Silent when unsure — anything still ambiguous after propagation gets no hint and falls through to the resolver / user. The oracle narrows or confirms; it never blind-guesses.

Failure modes (where the value is)

  • C(n) empty — the nickname's initial wells are not a subset of any oracle label: the instruction expects starting contents the oracle does not provide. Surface it.
  • I(n) empty — a pure destination labware with no initial contents: it trivially subsets everything, so it has zero discriminating power. Skip it.
  • An oracle label matched by no nickname — candidate for a "row unused" notice.

5. How it fits the resolver — and the override rule

  • Never overrides physical geometry. If the oracle claims wells a labware cannot physically have, that is a conflict, not an override. Geometry is truth.
  • Replaces the LLM guess. Where the resolver would hand 2+ survivors to the LLM, a confident oracle match wins — real data beats a guess. The oracle demotes the LLM to a fallback for what it cannot see.
  • Contradiction with a deterministic pick is a conflict to surface, not a silent flip.
  • Output: the forced bindings { nickname → config label } feed the resolver as external hints, consumed after the type filter.

6. What the oracle cannot resolve (the residual)

Exactly the cases the oracle structurally cannot see — these fall back to type / usage / user:

  • Non-well labware — tip racks, trash, temperature / magnetic modules, adapters: no contents, no shape signal.
  • Destination-only labware — empty at the start, so absent from the oracle.
  • Irreducible ties — two identical labware with identical contents: indistinguishable even with every hint, so the user picks (or slot / position decides).

7. Why this is the terminal deterministic step

After volume / capacity, occupied wells, well-shape, and type, the discriminating signals for contents-bearing labware are exhausted. A unique shape match is the strongest, data-grounded resolution. Beyond it lies only a guess (the LLM) or a genuine ambiguity (the user). So the oracle shape-match is the primary deterministic resolver for contents-bearing labware, with the LLM and the user handling only what the oracle cannot structurally see.
